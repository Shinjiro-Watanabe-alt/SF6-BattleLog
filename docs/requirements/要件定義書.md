# SF6-BattleLog 要件定義書

## 0. 文書について

本書はSF6-BattleLogの機能・データ・制約を定義する。コードの挙動を変更する作業では、同じラウンドで本書、`実装計画.md`、`テスト仕様書.md`を更新する。仕様変更はJSTの日付、旧仕様、変更理由を残す追記形式とする。

## 1. 目的・背景

### 1.1 解決したい課題

PS5でプレイするエドのランクマッチを、対戦直後の記憶と後日の動画分析の両方から蓄積し、勝ち筋・失点要因・練習対象を明確にする。一般的な戦績集計では残らない、立ち回り距離、ダメージの発生源、重要局面を個人用に記録する。

### 1.2 やりたいこと

- セット単位で結果、相手キャラ、平均距離、主なダメージ源・被ダメージ源、目立った出来事を記録する。
- 日次のYouTube限定公開動画を登録し、各セットに動画内時間を紐付ける。
- 動画分析結果をJSONで一括取込し、データを端末内で閲覧・書出しする。
- 重要局面をセットごとに参照し、動画の該当時間から再生して、次の対戦・練習へ反映する。
- 動画単位で分析依頼文とJSON雛形を作成し、Androidの共有機能からChatGPTへ渡せるようにする。

### 1.3 非対象

- カプコン／ストリートファイター6の非公開APIへの接続、ログイン自動化、規約を回避するデータ取得。
- 動画ファイルのGitHubへの保存、動画の自動アップロード、クラウド同期。
- 動画を機械学習で自動認識して分析する機能。初期段階では人間またはAIが作成したJSONを取り込む。
- 他ユーザー向けの共有、ランキング、課金機能。

## 2. 用語定義

| 用語 | 意味 |
|---|---|
| 動画ログ | 日付、タイトル、YouTube限定公開URLを持つ日次動画の記録 |
| セット | FT2の対戦結果。`2-0`、`2-1`、`1-2`、`0-2`で記録する最小分析単位 |
| 重要局面 | 勝敗の分岐、再現したい勝ち筋、繰り返す失点、要検証のいずれかに分類した動画内の時点 |
| 動画内時間 | 動画の先頭からの経過時間。`分:秒`または`時:分:秒`で記録する |
| 平均距離 | エドの立ち姿の横幅を1.0とした主な立ち回り距離。0.0〜4.0 |

## 3. システム全体構成

### 3.1 構成要素

| 要素 | 役割 |
|---|---|
| GitHub Pages | 静的PWAの配信 |
| ブラウザ／PWA | UI表示、入力、JSONの読書き、YouTubeへの遷移 |
| IndexedDB | セット・動画ログ・重要局面を端末ごとに保存 |
| YouTube限定公開 | 日次動画の保管とタイムスタンプ再生先 |

### 3.2 外部通信

アプリはGitHub Pagesから静的ファイルを取得し、ユーザーがタップした時だけYouTube URLを新しいタブで開く。動画内容・対戦記録・JSONを外部サーバーへ送信しない。

### 3.3 認証・機密情報

アプリは認証情報、APIキー、YouTubeアカウント情報を扱わない。YouTube URLはリンクを知る人が共有できる限定公開URLであるため、JSONやスクリーンショットを不必要に第三者へ共有しない。

## 4. スコープ定義

### 4.1 Phase 1: 手入力・動画分析基盤

- セット手入力、動画ログ、JSON書出し／取込、集計ダッシュボード。
- 重要局面タイムラインとYouTube該当時間への遷移。

### 4.2 Phase 2: 分析ライブラリ

- 重要局面を局面・評価・相手キャラ・練習対象で横断検索。
- 同じ失点や勝ち筋の頻度を集計し、練習対象を提示。

### 4.3 Phase 3: 外部データ連携

- 公式に許可された戦績・リプレイデータ取得方法を調査し、利用可能な範囲のみを連携。
- 上位エド使いとの比較、動画補助分析を検討。

### 4.4 フェーズ分割の理由

外部APIや動画認識を前提にせず、まず個人の振り返りに必要なデータ構造と分析フローを確立する。これにより、動画分析が手動でも継続でき、将来の連携先変更にも耐えられる。

## 5. 機能要件

### 5.1 起動画面・ダッシュボード

- 起動画面の最上部に、日付順の動画ログ一覧と`今日の動画を登録`導線を表示する。
- 動画カードには、セット数、勝敗・勝率、平均距離、未練習のトレモ項目数、主な勝ち筋・失点を表示する。
- 動画ログの下に、直近10セットの勝率、平均距離、要確認リプレイ数、次の確認点、最近のセットを表示する。

### 5.2 セット記録

- 相手キャラとセット結果を必須入力とする。
- ダメージ源・被ダメージ源は各最大3件とし、項目ごとに概算ダメージ帯を持つ。
- 目立った出来事は最大3件、各項目は未選択→1回→複数→未選択の順で切り替える。
- 平均距離を0.0〜4.0、0.1刻みで記録する。
- 動画ログと、任意の動画内開始・終了時間を紐付ける。

### 5.3 動画ログ

- 日付、タイトル、YouTube URLを必須入力とする。
- URLは`youtube.com`、`www.youtube.com`、`m.youtube.com`、`youtu.be`のみを受け付ける。
- 動画ログには紐付いたセット数とメモを表示する。
- 動画詳細では日ごとのセット数、勝敗・勝率、平均距離、要練習数、主な勝ち筋・失点を表示する。
- 動画詳細から、動画を紐付けた新規セットを追加できる。

### 5.4 分析依頼

- 動画詳細から、動画URL・日付・タイトル・対象セット数・JSON形式の依頼を含む分析依頼文を生成できる。
- Android等でWeb Share APIが使える場合は共有シートを開き、ユーザーがChatGPT等の共有先を選ぶ。アプリは共有先を指定・送信しない。
- 共有未対応時または明示操作時は依頼文をクリップボードへコピーする。
- 動画に紐付く既存セットと動画ログを含むJSON雛形を書出せる。ユーザーは分析結果を編集して既存IDで取り込む。

### 5.5 重要局面タイムライン（Phase 1・実装済み）

- セット詳細で重要局面を最大5件まで表示する。
- 各重要局面は動画内時間、局面、評価、内容、次回の行動を持つ。
- 局面は`中距離`、`攻め継続`、`起き攻め`、`端の守り`、`対空`、`ゲージ・SA`、`その他`から選ぶ。
- 評価は`勝敗の分岐点`、`再現したい勝ち筋`、`繰り返す失点`、`要検証`から選ぶ。
- 時刻ボタンをタップ時は紐付けたYouTube動画を該当秒数から新しいタブで開く。動画が未紐付けの場合は、時間情報を表示し、時刻ボタンを無効化して動画登録を促す。
- 次回の行動は短い具体的行動とし、`再現する`、`やめる`、`トレモで練習する`のいずれかを選べる。
- 各重要局面は編集・削除でき、削除前には確認を求める。

## 6. データモデル

### 6.1 Match

既存の`matches`ストアを維持する。`milestones`は`Match`内の配列で持つ。Phase 2の横断検索要件が確定した時点で、必要なら独立ストアへ移行する。

| フィールド | 型 | 必須 | 内容 |
|---|---:|:---:|---|
| id | string | ○ | UUID |
| createdAt | ISO 8601 string | ○ | 作成日時 |
| opponent | string | ○ | 相手キャラ |
| result | string | ○ | セット結果 |
| distance | number | ○ | 0.0〜4.0 |
| videoId | string/null | - | 動画ログID |
| videoStart/videoEnd | string | - | セット範囲 |
| damageSources/damageTakenSources | array | - | 最大3件のダメージ記録 |
| notableEvents | array | - | 最大3件の出来事 |
| milestones | array | - | 重要局面。最大5件 |

### 6.2 Milestone

| フィールド | 型 | 必須 | 内容 |
|---|---:|:---:|---|
| id | string | ○ | UUID |
| timestamp | string | ○ | `分:秒`または`時:分:秒` |
| phase | string | ○ | 局面分類 |
| evaluation | string | ○ | 評価分類 |
| summary | string | ○ | 起きたこと。120文字以内 |
| nextAction | string | ○ | 次回の行動。120文字以内 |
| actionType | string | ○ | `再現する`／`やめる`／`トレモで練習する` |
| reviewStatus | string | ○ | `未確認`／`確認済み`／`練習済み` |

## 7. 技術要件

- ランタイム依存なしのHTML/CSS/ES Modulesで実装する。
- IndexedDBは既存データを消さないバージョン移行のみ行う。
- Service Workerのキャッシュ名は更新時に上げ、旧キャッシュをactivate時に削除する。
- JSON取込は既存データへ追加／ID一致時は更新とし、確認ダイアログを出す。

## 8. 非機能要件

- 対戦後の1セット入力は短時間で完了できること。重要局面は分析時のみ入力する。
- オフライン時も既存記録の閲覧・入力を可能にする。
- データ消失に備え、JSON書出しを常時提供し、ブラウザへ永続化を要求する。

## 9. 開発・検証環境の制約

- CIはGitHub Actionsを手動実行する。
- 実機確認はAndroid端末のChromeまたはインストール済みPWAで行う。
- 開発環境でブラウザ自動テストが利用できない場合、JavaScript構文確認、JSON取込の静的確認、実機チェックリストで補完する。

## 11. 未決事項・今後の検討事項

- 重要局面を`matches`内の配列に持つか、横断検索を見越してIndexedDBの独立ストアにするかは、Phase 2の検索要件確定時に決定する。
- YouTube埋込み再生は、限定公開動画の表示可否とスマホの操作性を確認してから検討する。初期版は新しいタブで開く。
- 動画分析JSONをAIが生成する際の正式スキーマと、分析の受け渡し手順を実運用の試行後に確定する。

## 12. 変更履歴

### 2026-09-11: 重要局面タイムラインを実装

- 旧仕様: 重要局面は次ラウンド実装予定で、保存・表示・該当秒数再生ができなかった。
- 変更: `matches`内の`milestones`配列へ最大5件を保存し、詳細画面で追加・編集・削除・YouTube該当時刻遷移を可能にした。JSON書出し・取込にも含める。
- 理由: 動画分析の結果を、勝敗を分けた場面と次に実行する行動としてセット単位で再利用するため。

### 2026-09-11: 動画中心の起動画面と分析依頼導線を追加

- 旧仕様: 起動画面では全体ダッシュボードと最近のセットが先に表示され、動画ログはその後にあった。分析依頼はアプリ外で手入力していた。
- 変更: 起動画面の先頭を日別動画カードにし、動画詳細に日別サマリー、セット一覧、セット追加、動画再生、分析依頼の共有・コピー、分析JSON雛形の書出しを追加した。
- 理由: 1日1〜2本の限定公開動画を分析の作業単位として、記録・依頼・取込・振り返りを一続きにするため。
